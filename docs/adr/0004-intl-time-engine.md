# ADR-0004 — `Intl` as the time engine, with a bundled offset-table fallback

**Status:** accepted · 2026-09-23 · **the most important decision in the project**

## Context

Every time the app displays is derived from an IANA zone. Get this wrong and the product has no reason to exist — and the supplied mockups get it wrong four separate times (`01-design-audit.md` §8.1–8.2).

Options:

1. **Fixed offsets** — store `-8` per city. What the mockups did.
2. **`Intl.DateTimeFormat` with `timeZone`** — the platform's own tz database.
3. **Bundled tz library** — `luxon`, `@date-fns/tz`, `moment-timezone`, shipping tzdata in the app.
4. **`Temporal`** — the right long-term answer; not reliably available across RN 0.86 and all browsers today.

## Decision

**`Intl` as the primary engine, with a boot-time capability probe and a bundled offset-table fallback.** ~~A bundled `@date-fns/tz` fallback path~~ — corrected 2026-09-26: `@date-fns/tz` ships no tz data. Its `tzOffset` asks `Intl.DateTimeFormat` with `timeZone` (`node_modules/@date-fns/tz/tzOffset/index.js`), so on exactly the device this fallback exists for, it is wrong in exactly the same way. It stays a dependency only as a test cross-check.

## Rationale

- Option 1 is the bug. Offsets change twice a year and the rules themselves change by legislation — Lebanon reversed a DST decision mid-season in 2023 with days of notice.
- `Intl` reads the **OS** tz database. When a government changes the rules, an OS update fixes the app with no release. That is a property no bundled library can match.
- Bundling tzdata as the *primary* path means shipping an app update every time the rules change, and users who never update are permanently wrong.
- `Temporal` is the destination; revisit when it is stable across Hermes and all target browsers.

## The risk, and the mitigation

Hermes on some Android builds ships a reduced ICU. If `Intl.DateTimeFormat` **silently ignores** the `timeZone` option, every time in the app is wrong and nothing throws. This is the worst possible failure mode.

Therefore, at boot, before first render:

```ts
// 1 July 2025, 12:00 UTC → New York 08 (EDT), Tokyo 21
const ny = fmtHour('America/New_York', t)
const tk = fmtHour('Asia/Tokyo', t)
return (ny === '08' && tk === '21') ? 'full' : 'degraded'
```

Two zones, one mid-DST, one far from UTC. On `degraded`, the app switches its offset source to **`src/assets/data/tz.offsets.json`**, generated by `scripts/build-tzdata.ts` from Node's full ICU at build time: every IANA zone `Intl.supportedValuesOf` lists plus every dataset zone (432), with its offset and the minute of every change from 2024 through 2030. **35 KB raw, 5.6 KB gzipped.** Outside that window the nearest known offset is used — still exact for any zone without DST.

The engines differ in one function only. `zone.ts` computes every displayed value (hours, minutes, seconds, AM/PM, the date label, day/night, the day offset) as arithmetic from the offset, so a matching offset guarantees a matching display. The user is told once (`timeEngineDegraded` notice), and Settings → About shows *Time zone data: Built-in tables*. ~~Emits a telemetry event~~ — pending task 7.6 (Sentry); nothing is sent yet.

Both paths are asserted to agree (`src/domain/time/engine.test.ts`): the table matches `Intl` for **all 432 zones** a minute before and at every transition it records, and monthly across the window; and `getZonedTime` is identical under both engines for the 17 fixture zones at DST edges, in both 12h and 24h.

## Consequences

- ~~One extra dependency and ~60 KB~~ No extra runtime dependency; 5.6 KB gzipped, always bundled.
- **The table goes stale.** Re-run `npx tsx scripts/build-tzdata.ts` (a) before 2030 to extend the window and (b) when a government changes its rules — the primary engine picks those up from the OS, the fallback only from a release.
- Two code paths to keep in sync — kept honest by the shared test matrix.
- A device with a wrong *tz database* (very old, unpatched OS) can still be wrong. Accepted: the probe catches the catastrophic case, not the stale-by-one-rule case, and the weekly transition-table diff job surfaces that class of drift.
- **Derived rule, enforced by `/tz-audit`:** the only persisted time fact anywhere in the codebase is an IANA zone ID. A literal `-8`, `"UTC-8"` or `"PST"` in `src/` is a build failure.
